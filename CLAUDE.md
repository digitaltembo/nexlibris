# nexlibris

Calibre-like library manager. [PLAN.md](PLAN.md) is forward-facing: the vision, guiding decisions, and what is left per milestone (M1, M6, M13, M7, M4, M8–M12, in planned order; numbers are names, not an order), kept concise; keep it current when scope or decisions change, and drop work once done (git history has it). Its **TLDR** section (status table and next steps) must be updated in the same change whenever work moves a milestone forward. The README describes the architecture.

## Layout

- `common/` (`@nexlibris/common`): the library model, shared by every frontend and backend.
  - `types.ts` schema (an item's `metadata` is a `BookMetadata`: fixed fields such as `titleSort`, `authorSort`, `published`, `originallyPublished`, `language` and `coverColor`, plus any custom keys); `metadata.ts` normalizing its values (re-exported from tools' `metadata.ts`, which also holds `BookMetadata`, `Creator` and `MetadataValue`: partial ISO dates, with a minus for years before AD 1, `-0570` being 570 BC with no year 0; Calibre's midnight-UTC timestamps rounded to the day; numbers), dates for reading and in order (`formatDate`, `formatYear`, `compareDates`; sort and compare dates with these, not as strings) and sort names (`titleSortOf`, `nameSortOf`); `operations.ts` typed operations and the pure `applyOperation` reducer; `backend.ts` `LibraryBackend` and `StoredLibraryBackend` (library JSON + change log + content-addressed files on any `Storage`).
  - `search.ts` the search syntax, `bookFields.ts` the fixed fields' labels and sort keys and `metadataText.ts` values as text (the client's, kept here so the server searches as the app does); `catalog.ts` a connection's catalog (`deviceItems`, `deviceItemFiles`). `opds.ts` OPDS feeds of books, for serving live: arranged as the Library browses (`arrangeFeeds`, `feedCategories`), as pages (`bookPage`, `navigationPage`) whose links the caller chooses, written as OPDS 1.2 Atom (`atomFeed`) or OPDS 2.0 JSON (`opds2Feed`); `opdsServer.ts` serving them (`serveOpds`): each served feed connection (`opds.served`, `OPDS_SERVED_TYPE`; nothing to do with the static export, which writes its own in `client/src/devices/opds/`) at `<root>/<id>/`, current at every request, `.xml` or `.json` (else by `Accept`), searched with `search.ts`, its books' files and covers handed back for the caller to stream; the server serves it (`server/src/api/opds.ts`).
  - `storage.ts` the `Storage` interface, which can delete (`remove`; `MemoryStorage` for tests), and optionally move and prune emptied folders (`moveFile` falls back to copying; `prefixedStorage` a storage's subfolder).
  - `placedLibrary.ts` a library in a folder of the user's (`PlacedLibraryBackend`): its own files in `.nexlibris/` (as `StoredLibraryBackend` keeps them, plus `layout.json` and `placed.json`, where each book file is by hash), the books where a `FileLayout` (path templates) puts them, by a `Placer` the client supplies (`client/src/library/fileLayout.ts`), moved in the background after each change. `servedLibraryPath` is what the desktop app serves by URL. `libraryFolderApi.ts` the desktop and phone apps' choosing and moving of the library's folder, and (desktop only) showing a book's file in the system's file manager (`showFile`; "Show in folder" in `components/ItemFiles.tsx`, offered only there, by `canShowFiles` in `client/src/library/libraryFolder.ts`). The backend deletes files with `deleteFile`/`deleteLocalFile`; `client/src/library/freeFiles.ts` deletes the files of deleted books that nothing else uses.
  - `syncApi.ts` M6's sync API (a hub serves it; `pair`, `hello`, `state`, `apply`, `done`, `missing`, plus files streamed at `api/sync/files/<hash>`), `sync.ts` running a sync from the instance that drives it (`previewSync`, `runSync`, `pairWithHub`) and the hub's side (`createSyncService`), `syncHttp.ts` the API and files over `fetch`, `syncFiles.ts` moving files after a sync (`transferFiles`) and fetching missing ones on read (`fetchingMissingFiles`); `syncHostApi.ts` the desktop page's control of hosting (desktop only), `peerApi.ts` the phone apps' relay of sync calls and files (Android and iOS), `localHttpApi.ts` their relay of calls to devices on the local network such as CrossPoint readers (`relayedFetch`, local addresses only, bodies in chunks; Android and iOS; the client's `devices/localFetch.ts` picks it or `fetch`). `windowApi.ts` the phone apps' colours behind the system bars (Android and iOS; set by `client/src/styles/windowColors.ts` to the theme's background, or the reader's while epubier shows a theme of its own).
  - Other transports, with the phone as hub: `syncMessage.ts` the API's calls as chunked messages (`messageFetch`; the framing is mirrored in `android/.../BluetoothFraming.kt` and `ios/NexlibrisKit/.../BluetoothFraming.swift`, keep the three in step), `syncHub.ts` a hub in TypeScript (pairing, calls, files) that the Android page runs for Bluetooth, `bluetoothApi.ts` the GATT UUIDs and the phone apps' bluetoothHost API, `folderHub.ts` a replica library in a shared folder acting as hub (USB), `usbFolderApi.ts` the phone apps' sync folder as storage (Android and iOS; on iOS a folder picked in Files that a computer also reaches, as iOS shows no folders over USB).
  - `scope.ts` what a hub shows an instance: only the books in its connection's catalog (a `ScopeRule` the client supplies, `instanceScope`) plus those it has, with everything naming other books cut out of the library and the changes sent. `createSyncService` with a `scope` (network and Bluetooth hubs; not the folder hub or the server) applies it to the peer its host names (`fromPeer`), and to its files (`allows`, which the desktop host and Bluetooth hub ask before sending one). Each side exposes only its catalog for the other: the driver sends only what `SyncOptions.expose` picks, and offers the hub the rest (`SyncPreview.offer`, kept there as `sync-offers`, `peerOffer`; asked for with `requestFromPeer`, sent with the next sync). Books only one side has move by `pull` and `push` (Sync from, Sync to, or some books), books both have merge, the state hash covers only those (`ApplyRequest.compare`), and deletions never cross: a book deleted on one side is kept off it there (`Device.excluded`).
  - `merge.ts` M6's merge of two instances as a pure function (`planMerge`, by targets an operation writes); `repair.ts` the state hash checked after a merge (`stateDigest`) and the repair from the source of truth (`planRepair`). Their tests share a seeded random edit generator; keep both random tests passing.
  - `storageApi.ts` the Storage API defined with estuary-rpc; `saveApi.ts` saving files out of the app; `importApi.ts` native file and folder picking for import (the app stores picked files itself); `rpc.ts` estuary-rpc over a message channel; `rpcStorage.ts` `Storage` over that API (base64 chunks).
- `tools/` (`@nexlibris/tools`): working with books' files, standalone (no other nexlibris package, no React), so other projects can use it. Imported by module, `@nexlibris/tools/formats/formats` and so on (its `exports` map `./*` to `src/*.ts`), so heavy modules still load only where they're used. `@nexlibris/common` builds on it, not the other way round.
  - `metadata.ts` books' metadata as files and the library keep it (`BookMetadata`, `Creator`, `MetadataValue`, part of a library's stored shape, so changing them means a migration in common) and normalizing it (dates, numbers, sort names, `mergeTags`).
  - `formats/` metadata and cover extraction per format (EPUB, MOBI/AZW3, PDF, TXT/RTF, CBZ/CBR; CB7 only by its name, as there's no 7-Zip reader in the tools; `parseFile.ts` the one entry, loading each format's library on first use; `opf.ts` an OPF's metadata, an EPUB's or a Calibre `metadata.opf`; `epubMetadata.ts` writing metadata into an EPUB, `epubBuilder.ts` making one; `kindleHeader.ts` a Kindle file's metadata from its headers alone, `kindleMetadata.ts` writing it, as Calibre's `ebook-meta` does: each MOBI header record's EXTH and full name rebuilt within the record's padding where it fits, else the later records moved along, both header records of a joint MOBI/KF8 file (the KF8 one at EXTH 121), the text untouched; no series or sorts, which Kindle files can't hold; `fixtures/sample-joint.mobi` is a joint file Calibre made; `rar.ts` writing RAR 5 archives, files stored, for the cbz-cbr converter), `formats/mobi/` writing Kindle books from EPUBs (`write.ts`, converters epub-azw3, epub-mobi and epub-azw, after Calibre's MOBI writer, checked with `calibre-debug -m` and `ebook-convert`): `epub.ts` an EPUB's package (spine, nested table of contents, guide), `kf8.ts` AZW3 as KF8 (the HTML and CSS kept, split into skeletons and fragments, links as `kindle:pos`, the chunk, skeleton, guide and NCX indexes), `mobi6.ts` MOBI and AZW as MOBI 6 (one document in Mobipocket markup, what the CSS says turned into tags and attributes by the cascade in `css.ts`, links as `filepos`, a flat NCX, a contents page where the book has none), sharing `records.ts` (PalmDOC records, EXTH, indexes; `palmdoc.ts` the compression), `book.ts` (the metadata, cover and images; `resources.ts` images Kindles show, fonts) and `tbs.ts`) and `formats/convert/` in-browser conversion (a converter's `ConvertContext.item` is any record with a title, creators, identifiers, tags and metadata, as an `Item` is): `rtf.ts` EPUB to RTF; `pdf/` an EPUB typeset as a PDF with pdf-lib and fontkit (Literata and JetBrains Mono embedded, the mono font without ligatures, which crash fontkit), its options in `pdf/options.ts` (page size, book and chapter headers, page and chapter numbers, roman numerals); `pdfText/` a PDF's text layer reflowed as an EPUB, after `~/dev/scan2epub`'s `core/` (`textLayer.ts` pdf.js's runs as lines of words, `layout.ts` lines classified against the book's statistics per side of the page: running heads, folios and heads or feet repeated page after page left out, headings and chapter openings found; `reflow.ts` paragraphs by indents, gaps and short lines, across pages too, hyphens at line ends judged by the book's own spellings, typography, printed headings parsed), chapters from the PDF's bookmarks else its openings, and each side's margins to ignore as options; no OCR (tesseract-wasm is too big for tools), so a PDF without a text layer is refused, and pages that are pictures are kept as images only where there's a canvas. Conversions in the app (`client/src/library/convert.ts`) run a path of converters, keeping only the last output, its `derivedFrom.converter` the ids joined with `+`; a book's Convert… (`components/ConvertDialog.tsx`: from one of its files, to any format reached, indirect ones warned of) and Bulk convert (`components/BulkConvertDialog.tsx`, from a format or each book's easiest file, `conversionSource`) are the only ways to convert by hand. Plugins add formats and converters through a registry: a plugin's package names its format ids in `PluginFormats` by declaration merging, and the app calls `registerFormats` and `registerConverters` before anything reads them (`FORMATS`, `EPUB_FORMATS`, `CONVERTERS` and the other lists are filled in place); `FormatInfo.epub` marks EPUB variants, `isEpub`, `EPUB_FORMATS`; compound extensions like `x4.epub` by `formatFromName`/`stripExtension`. Converters' options are `OptionField`s (`options.ts`), which the client's `SettingField` extends. Tools knows no particular plugin.
  - `fulltext/` the text of books for full-text search: `extract.ts` a file's text in sections (EPUB spine items with chapter names and CFI paths per text node, and TXT, read with `markup.ts`, htmlparser2 rather than the DOM, so they work in a worker; PDF pages and RTF in the page, `extractPage.ts`; `textFormats`, `workerFormats`), `match.ts` queries, word lists and passages (each with its chapter and the locator the reader opens at); bump `EXTRACTOR_VERSION` when extraction changes.
  - `coverColor.ts` a cover's most prominent colour (`coverColor`), set at import, on Add by ISBN and by re-reading; the client's `components/Cover.tsx` fills a loading cover with it.
  - `zip.ts` zips written and read a piece at a time (ZIP64, deflate by `CompressionStream`), stored files passed through as the caller's Blobs, for backups too big for memory (`client/src/library/backup.ts`).
- `crosspoint-tools/` (`@nexlibris/crosspoint-tools`): files for CrossPoint readers, over `@nexlibris/tools` (imported by module, as tools is). `formats.ts` and `convert.ts` the `x4.epub`/`x3.epub` formats and their converter (registered by the client's `plugins/formats.ts`), `xteink/` the X4/X3 optimizer, a port of the Python in `~/dev/crosspoint/calibre-plugins/crosspoint_reader/` (keep it in step with `optimizer.py`/`textsplit.py`; its options live in `xteink/options.ts`, are part of the converter version, and are asked for when converting, a converter's `options`/`withOptions`, shown by `client/src/components/ConvertOptions.tsx` in Convert and Bulk Convert only when the conversion chosen runs that converter), `sleepImage.ts` sleep images as screen-sized grayscale BMPs, `stardict.ts` StarDict dictionaries unpacked and checked, `fonts.ts` fonts sorted into families, and `libraryIndex.ts` the reader's `/.crosspoint/library.idx`, a port of `~/dev/crosspoint/crosspoint-reader/docs/files/library_idx.ksy` (keep it in step with that).
- `cli/` (`@nexlibris/cli`, the `nexlibris` command): tools and crosspoint-tools on the command line (`info`, `cover`, `convert`, `set`, `formats`; usage in `src/args.ts`, the commands in `src/commands.ts`). `src/environment.ts` gives the tools what they need of a browser under Node, imported first: happy-dom's `DOMParser`, `XMLSerializer`, `Node` and `document`, and `fetch` of local files (bundled assets, the Kindle parser's resources). `src/canvas.ts` gives them a canvas from `@napi-rs/canvas` (`createImageBitmap`, `OffscreenCanvas`, `<canvas>`), so PDFs get covers and images are re-encoded (the CrossPoint optimizer, Kindle images) as in a browser; every conversion and tool works in both. Bundled with rolldown (`dist/main.js`): packages stay external, except rtf.js (its entry imports its bundle without an extension); `nodeBuilds.ts`, shared with the tests' `vite.config.ts`, makes Vite's `?url` imports `import.meta.resolve` (resolved at once in tests) and pdf.js its legacy build, the one for Node. Conversions chain where there's no direct one (tools' `conversionPath`/`conversionPaths` in `formats/convert/converters.ts`, with `pathOptions` and `pathWithOptions`, which the app uses too), by the highest fidelity (`Converter.fidelity`, 1 for nothing of value lost towards 0, which every converter, plugins' too, must say; a chain's `pathFidelity` is the product of its steps', ties going to fewer steps), so plain text, which keeps only the words, is a step only where nothing else reaches; `nexlibris convert --help` prints which formats convert to which (`conversionMatrix`, from the converters registered), and the same table is written by hand in the README's Conversions and, direct conversions only, `tools/README.md`: keep both in step when converters change, as the lists of formats read, given covers, written, read in the app and searched are with what the tools do (the CLI's `USAGE`, the README's Formats, `tools/README.md`); the Kindle parser is given a temporary folder for its files. `set` writes EPUBs and Kindle files, through `writeEpubMetadata` and `writeKindleMetadata`, so it changes and adds values but can't clear them (and refuses series and sorts for Kindle files).
- `client/` (`@nexlibris/client`): React + Vite web app. Formats, conversion, cover colours, zips and text extraction come from `@nexlibris/tools`, CrossPoint's files from `@nexlibris/crosspoint-tools`; `plugins/formats.ts` registers plugins' formats and converters with tools, imported first by every entry point (`main.tsx`, `fulltext/text.worker.ts`, the tests' setup in `vite.config.ts`, Storybook's preview); connections only send the files a book has, as stored, in their `formats` order; they never convert or rewrite.
  - `backends/` OPFS storage (browser) and the Android, iOS and desktop bridges. `library/LibraryContext.tsx` picks one: the native app's storage when there's a transport (`backends/native.ts`: Android's bridge, iOS's message handler or the desktop app's `window.NexlibrisDesktop`), otherwise OPFS. In the apps `NativeStorage` reads stored files by fetching `/library/files/…`, which the app serves; everything else goes over the transport.
  - `isbn/` ISBN checking, Open Library lookup and barcode reading (native `BarcodeDetector`, else zxing-wasm, whose wasm is bundled rather than fetched from its CDN); the "Add by ISBN" UI is `components/IsbnDialog.tsx`, and Open Library's covers for a book (`findCovers`, by ISBN, then title and author), offered in the book editor by the edit button over its cover (`components/CoverPicker.tsx`, a dropdown: choose an image, find on Open Library, or generate one, `library/generateCover.ts`, title and authors on a random muted colour; saved by `library/editCover.ts`, with its colour, the old cover freed).
  - `devices/` the connection model (`types.ts`: a `ConnectionType` reads (`read`: lists a place's books and brings them in), writes (`write`: has a catalog; `single` if it takes books one at a time), or both, and is one of: a `FilesType`, books as files at paths (a reader, a folder; `tools` manage other things on it, each a tab beside its books on the "On it…" screen), an `ExportType`, the static OPDS catalog, an `InstanceType`, another nexlibris, a `FeedType`, an OPDS server browsed, or a `ServedType`, a feed the account's server serves; `formats` it takes, best first, and `preferred` ones it asks to convert to; `SettingField` kinds text, checkbox, `some`). A write connection's **catalog** (`selection.ts`) is `Device.items` (and `Device.files` for books held by particular files) plus what its search matches, added for good when it's opened or synced (`catalogAdditions`); taking a book out (`takeOutOfDevice`) keeps it out of the search too (`excluded`), adding it by hand (`addToDevice`, `addFileToDevice`) lets it back. The sync planner/runner (`plan.ts`, `run.ts`) only adds: books in the catalog not there are sent, files it sent that changed are replaced, nothing else is removed, and a book deleted on the device is taken out of the catalog rather than sent again (`SyncPlan.deleted`); a book whose path changes is moved where the target can, `DeviceTarget.move`, else sent again; files linked by hand, `PlacedFile.linked`, stay put while current; copies of chosen books found on the device, by `devices/match.ts`, are kept or moved into place rather than sent, `PlacedFile.found`; `PlanOptions.only` sends just some books and leaves the rest of the device alone, which `components/SendTo.tsx` ("Send to…" in a book's details and Send in Bulk edit) uses after adding them to its catalog; `components/AddTo.tsx` ("Add to…", on a book or one of its files) only adds them. `send.ts` what to ask before sending (`checkSend`: books without a preferred format a converter can make, files behind their metadata), asked by `components/SendCheck.tsx` in every send and Sync to. `pathTemplate.ts` where books go on a device (`FilesType.folder` and `fileName` are templates: `/library/<author>/[<series>/]`, made safe for FAT), `contents.ts` (what's on a connection against the library, with linking, importing (a type's own `download` first, a folder's manifest) and removing: a book removed from a device is taken out of its catalog, `removeOperations`), and `devices/opds/` the OPDS catalog export (calibre3opds's layout; book files only ever added; `cloudflare/` calibre3opds's Pages files, copied verbatim and written by `cloudflareFiles`, with `search-index.json` for search routing) and its remembered folders. The UI calls them connections (`components/ConnectionsDialog.tsx`: Edit, On it…, Sync from and Sync to by what each can do); the stored model still calls them devices (`library.devices`). A book's details list the catalogs holding it (`components/ItemCatalogs.tsx`). `connections/` the built-in connection types (`index.ts`: `CONNECTION_TYPES`, `connectionType`, `readableConnections`; `active.ts` whether each is active on this device, by its type's `activation`: always (OPDS server and export), by hand (CrossPoint, twins; kept in local state, `active-connections`, so per device), or checked (a folder: chosen here and still there); only active ones are in the Library and can be sent to, and Send to… shows the others as inactive): `opds.ts` the OPDS server, the static export (its formats and Cloudflare settings) and the feed the server serves (`opdsServed`: a catalog with nothing to sync, active and offered only while signed in to a server, its address `servedFeedUrl`), `instance.ts`, `folder/` a folder as backup or drive (`FolderTarget` over a `FileSystemDirectoryHandle` remembered per computer, `.nexlibris-library.json` written after each sync by `manifest.ts`, books read back with their details; needs `showDirectoryPicker`). Read connections other than OPDS servers are browsed in the Library too (`['connection', id]` in `browse.ts`, `components/ConnectionBrowser.tsx`). `plugins/` built-in plugins, each adding connection types, formats, converters and/or views (`views/types.ts`: a `LibraryViewType`, a way of showing the books beside grid and list, offered by `views/views.tsx` in the switcher, the View menu and Settings) (`bookshelf/`: the CSS 3D bookshelf view; `graph/`: the force graph view, after `~/Documents/readings`, books joined by their authors, tags and series (`graph.ts`, tags on a quarter of the books left out as hubs) and drawn with 3d-force-graph in the theme's colours (`ForceGraph.tsx`, loaded lazily since three.js is large; the glow only in the dark scheme); `crosspoint/`: the reader type (`crosspoint.reader`, its Model setting X4 or X3 picking the preferred `x4.epub` or `x3.epub`), those formats, their converter and the reader's files from `@nexlibris/crosspoint-tools`, the CrossPoint web API client (`client.ts`; `fakeReader.ts` an in-memory reader for tests and stories), its device tools in `tools/` (sleep images, StarDict dictionaries, fonts), and the reader's `library.idx` read by crosspoint-tools' `libraryIndex.ts`).
  - `library/libraryFolder.ts` where the library is kept (browser storage, the desktop app's data folder, Android's own storage, or a folder the user picks, laid out by `library/fileLayout.ts` with CrossPoint's path templates; a browser needs `showDirectoryPicker`, so Chrome or Edge), opening it (`LibraryContext` uses it; a browser asks permission for its folder again with a click) and moving it (`relocate` in the browser, copying between folder handles; the apps move it natively behind `libraryFolderApi.ts`: the desktop main process, `desktop/src/libraryFolder.ts`, and Android, `LibraryFolderService.kt`; `LibraryPlace.native` is the app's side). The UI is `components/LibraryFolderDialog.tsx` ("Library folder…"), which says what a folder costs outside the desktop app (slower writes; in a browser, permission asked again after a restart).
  - `library/importFiles.ts` imports: groups files into books (a Calibre book folder with `metadata.opf`, else by name minus the format), takes a Calibre folder's metadata, cover and rating, and matches books already in the library (UUID, ISBN, title and author). Folders come from a folder input, dropped folders (`library/droppedFiles.ts`), or the apps' folder pick (`library/nativeImport.ts`).
  - `library/thumbnails.ts` covers as shown: thumbnails made once and kept in the backend's local files (`readLocalFile`/`writeLocalFile`, under `local/`; not synced or backed up), at `local/thumbs/`, which the apps serve at `/library/local/thumbs/…` as they serve `/library/files/…`. `components/Cover.tsx` shows a thumbnail only while near the viewport; don't display full-size covers in lists.
  - `library/currentlyReading.ts` Currently Reading: books with a reading position that isn't finished or set aside (`ReadingPosition.setAside`, which keeps the place; reading again clears it), shown by `components/CurrentlyReading.tsx` in a notice above the books (`NoticeBox` in `styles/ui.ts`); one click reopens a book at its place. The notice shows each time the app opens while books are being read, until its Hide (not remembered); the Library lists them too, as Currently reading beside All books (`['reading']` in `browse.ts`, last read first unless sorted).
  - common's `bookFields.ts` the fixed fields' labels and kinds as the UI shows and edits them, and the sort keys (title and author sort, falling back to computed ones; first published).
  - `library/dedupe.ts` items with the same title and authors and merging them (as operations); `library/reread.ts` re-reading metadata from the books' own files, filling in only what items lack (never online). `library/fileMetadata.ts` the fingerprint of the metadata written into a file (`FileRef.metadataKey`: set at import when the file says what the item says, by conversion, and by updating files; with the cover's hash for files given the cover, `writesCover`: EPUBs not converted from another, as the CrossPoint optimizer makes its own; a fingerprint without it says nothing of the cover), so a file whose item's metadata changed since is behind it (`isBehind`, shown in `ItemFiles.tsx`). `library/updateFiles.ts` writing the library's metadata and cover into its EPUBs where they say otherwise (`writeEpubMetadata` in tools' `formats/epubMetadata.ts`, whose `cover` replaces the book's cover image, renamed for another type, or adds one; DRM-protected files, `epubDrm`, are left alone), each new file checked to read back as the library has it before it replaces the old one, with converted files, reading positions and the text index (`TextIndex.carry`) moved to it. The UI is `components/CleanupDialog.tsx` ("Clean up library…"), a list of cleanups each behind a button, where further cleanups go.
  - Open Library is called only on explicit user action (Add by ISBN, Find on Open Library for a cover); nothing looks things up online on its own.
  - common's `search.ts` the search syntax (Gmail-style `field:value` terms, `or`, `has:`; documented at its top) the one way of choosing books: the search box, connections' catalogs and the books another instance keeps (`components/QueryInput.tsx`, a text box with its match count), categories. There are no separate filters or rules; `library/suggest.ts` completes field names and values in the search dialog (`searchFields`, `fieldSuggestions`).
  - `fulltext/` full-text search, over tools' `fulltext/` (extraction and matching): `textWork.ts` the heavy work run in a Web Worker (`text.worker.ts`, over `workerRpc.ts`; in the page in tests): extracting, packing (gzipped JSON) and searching, with the word lists it has read cached; `textIndex.ts` the index in the backend's local files (`fulltext/<hash>.json.gz` and `.words.json.gz`, listed in local state's `fulltext`; not synced or backed up), `TextIndexContext.tsx` indexing in the background and `useTextSearch`. The search dialog's "Inside books" mode and `components/TextResults.tsx` show it.

## Conventions

- Mutate libraries only through operations; never edit `Library` objects directly in the UI.
- Changing the stored shape of a library (types in `common/src/types.ts` or `tools/src/metadata.ts`, or an operation's shape) means bumping `SCHEMA_VERSION` and adding a step to `MIGRATIONS` in `common/src/migrate.ts`, with a test.
- Prefer TypeScript implementations of format parsing and conversion that run in the browser, in `tools/`.
- Styling uses styled-components with transient `$props`; theme values are CSS variables in `styles/GlobalStyle.ts`, dark when the system is unless Light or Dark is picked in Settings (`styles/appearance.ts`, `<html data-theme>`); code that needs to know reads `isDark`/`onAppearanceChange` there rather than `prefers-color-scheme`. Reuse `styles/ui.ts` before adding new primitives. No CSS files.
- Text the client shows goes in `client/src/i18n/en.json` and is read with `t`/`tn`, never written inline in components or messages (keep the English as it is when moving it; tests read it). Plurals are plural objects chosen by `count`, not `n === 1` in code; join lists with `common.listJoin`.
- Book HTML (descriptions, EPUB content) is untrusted: render it with `RichText`, which rebuilds allowlisted tags as React elements. Never use `dangerouslySetInnerHTML`.
- Tests run in happy-dom with resource loading disabled (each package's `vite.config.ts`); keep it that way so tests never hit the network. Sample books live in `tools/src/formats/fixtures/`. happy-dom differs from browsers: parse XML with tools' `formats/xml.ts` (happy-dom rejects some valid XML declarations), and mock the Kindle parser in import tests (under Node it fetches resources and writes to disk).
- Code style: single quotes, lines around 120 columns (some run longer). There's no formatter config, so don't run Prettier over whole files: it rewraps untouched code. Format only what you write, by hand or on a scratch copy.
- Any change to the Storage, Save or Import API must be made in `common/src/storageApi.ts`/`saveApi.ts`/`importApi.ts`, `android/.../RpcRouter.kt` plus `StorageService.kt`/`SaveService.kt`/`ImportService.kt`, `ios/NexlibrisKit/.../RpcRouter.swift` plus `FileStorage.swift`/`SaveService.swift`/`ImportService.swift`, and `desktop/src/fileStorage.ts`/`saveService.ts`/`importService.ts`, with tests on every side. The SyncHost API is desktop-only; the Peer, localHttp, bluetoothHost, usbFolder and window APIs are Android's and iOS's (change both).
- Save files out of the app with `client/src/library/saveFile.ts`, not `<a download>` alone: downloads do nothing in the Android WebView. For big files use `saveParts` (the backup does, with tools' `zip.ts`), and call it before awaiting anything so Chrome's save picker still has the click's user activation.

## Dependencies to know about

- `epubier` is from npm; its source is `../epubierjs`, where changes are made and published (to try one before publishing, link it again, `"epubier": "file:../../epubierjs"` in `client/package.json`, and run `npm run build` there after each change, as nexlibris uses its built `dist/`). Its `position` and `onLocationChange` options exist for nexlibris's reading positions, `onThemeChange` for colouring Android's system bars like the reader, `toolbar` and `share` for leaving out its buttons (nexlibris leaves out fullscreen, every share button, and back in a book's own window) `titleBar` for its toolbar moving the desktop app's window, and `browserFullscreen: false`, `onFullscreenChange` and `setFullscreen` for its fullscreen being that window's, and `replacements: 'base64'` for opening image-heavy books quickly in the Android WebView; `src/formats/epub/patches.js` there fixes epub.js's base64 mode. Its PDFs, Kindle books and RTF need its peers `pdfjs-dist`, `@lingo-reader/mobi-parser` and `rtf.js`, which the client depends on, deduplicated by `resolve.dedupe` in `client/vite.config.ts` (a linked epubierjs has its own copies). The client's build compiles rtf.js (epubier's and the tools') from its source with only the single-byte code pages (`rtfCodepages` in `client/vite.config.ts`), as epubier's own script does, rather than its 2mb of tables; the dev server and tests keep rtf.js's own build.
- `estuary-rpc`, `estuary-rpc-client` and `estuary-rpc-server` are from npm; their source is `../estuary-rpc`, where changes are made and published (to try one first, link them again, `file:../../estuary-rpc/<package>` in `common/` and `server/`, built with `npx tsc` in each package). Vite pre-bundles them (`optimizeDeps`), as their `dist/` is CommonJS. `rpc.ts` keeps its own client types (`MessageClient`), which estuary's clients are cast to (`httpClient` in `common/src/rest.ts`).
- Over HTTP, APIs follow estuary-rpc's REST conventions (200 JSON, 204 for none, errors `{ status: 'error', message }` with a status, thrown on the client as `ApiError`): the server with estuary-rpc-server, clients with estuary-rpc-client over `fetch` (`httpClient`, `reaching`), and hubs that relay calls to the page (desktop, Bluetooth) answering with `restReply`. No envelopes of our own on the wire.
