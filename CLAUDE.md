# nexlibris

Calibre-like library manager. [PLAN.md](PLAN.md) is forward-facing: the vision, guiding decisions, and what is left per milestone (M1, M6, M13, M7, M4, M8–M12, in planned order; numbers are names, not an order), kept concise; keep it current when scope or decisions change, and drop work once done (git history has it). Its **TLDR** section (status table and next steps) must be updated in the same change whenever work moves a milestone forward. The README describes the architecture.

## Layout

- `common/` (`@nexlibris/common`): the library model, shared by every frontend and backend.
  - `types.ts` schema (an item's `metadata` is a `BookMetadata`: fixed fields such as `titleSort`, `authorSort`, `published`, `originallyPublished`, `language` and `coverColor`, plus any custom keys); `metadata.ts` normalizing its values (partial ISO dates, with a minus for years before AD 1, `-0570` being 570 BC with no year 0; Calibre's midnight-UTC timestamps rounded to the day; numbers), dates for reading and in order (`formatDate`, `formatYear`, `compareDates`; sort and compare dates with these, not as strings) and sort names (`titleSortOf`, `nameSortOf`); `operations.ts` typed operations and the pure `applyOperation` reducer; `backend.ts` `LibraryBackend` and `StoredLibraryBackend` (library JSON + change log + content-addressed files on any `Storage`).
  - `storage.ts` the `Storage` interface, which can delete (`remove`; `MemoryStorage` for tests), and optionally move and prune emptied folders (`moveFile` falls back to copying; `prefixedStorage` a storage's subfolder).
  - `placedLibrary.ts` a library in a folder of the user's (`PlacedLibraryBackend`): its own files in `.nexlibris/` (as `StoredLibraryBackend` keeps them, plus `layout.json` and `placed.json`, where each book file is by hash), the books where a `FileLayout` (path templates) puts them, by a `Placer` the client supplies (`client/src/library/fileLayout.ts`), moved in the background after each change. `servedLibraryPath` is what the desktop app serves by URL. `libraryFolderApi.ts` the desktop and phone apps' choosing and moving of the library's folder, and (desktop only) showing a book's file in the system's file manager (`showFile`; "Show in folder" in `components/ItemFiles.tsx`, offered only there, by `canShowFiles` in `client/src/library/libraryFolder.ts`). The backend deletes files with `deleteFile`/`deleteLocalFile`; `client/src/library/freeFiles.ts` deletes the files of deleted books that nothing else uses.
  - `syncApi.ts` M6's sync API (a hub serves it; `pair`, `hello`, `state`, `apply`, `done`, `missing`, plus files streamed at `api/sync/files/<hash>`), `sync.ts` running a sync from the instance that drives it (`previewSync`, `runSync`, `pairWithHub`) and the hub's side (`createSyncService`), `syncHttp.ts` the API and files over `fetch`, `syncFiles.ts` moving files after a sync (`transferFiles`) and fetching missing ones on read (`fetchingMissingFiles`); `syncHostApi.ts` the desktop page's control of hosting (desktop only), `peerApi.ts` the phone apps' relay of sync calls and files (Android and iOS), `localHttpApi.ts` their relay of calls to devices on the local network such as CrossPoint readers (`relayedFetch`, local addresses only, bodies in chunks; Android and iOS; the client's `devices/localFetch.ts` picks it or `fetch`). `windowApi.ts` the phone apps' colours behind the system bars (Android and iOS; set by `client/src/styles/windowColors.ts` to the theme's background, or the reader's while epubier shows a theme of its own).
  - Other transports, with the phone as hub: `syncMessage.ts` the API's calls as chunked messages (`messageFetch`; the framing is mirrored in `android/.../BluetoothFraming.kt` and `ios/NexlibrisKit/.../BluetoothFraming.swift`, keep the three in step), `syncHub.ts` a hub in TypeScript (pairing, calls, files) that the Android page runs for Bluetooth, `bluetoothApi.ts` the GATT UUIDs and the phone apps' bluetoothHost API, `folderHub.ts` a replica library in a shared folder acting as hub (USB), `usbFolderApi.ts` the phone apps' sync folder as storage (Android and iOS; on iOS a folder picked in Files that a computer also reaches, as iOS shows no folders over USB).
  - `scope.ts` what a hub shows an instance: only the books in its connection's catalog (a `ScopeRule` the client supplies, `instanceScope`) plus those it has, with everything naming other books cut out of the library and the changes sent. `createSyncService` with a `scope` (network and Bluetooth hubs; not the folder hub or the server) applies it to the peer its host names (`fromPeer`), and to its files (`allows`, which the desktop host and Bluetooth hub ask before sending one). Each side exposes only its catalog for the other: the driver sends only what `SyncOptions.expose` picks, and offers the hub the rest (`SyncPreview.offer`, kept there as `sync-offers`, `peerOffer`; asked for with `requestFromPeer`, sent with the next sync). Books only one side has move by `pull` and `push` (Sync from, Sync to, or some books), books both have merge, the state hash covers only those (`ApplyRequest.compare`), and deletions never cross: a book deleted on one side is kept off it there (`Device.excluded`).
  - `merge.ts` M6's merge of two instances as a pure function (`planMerge`, by targets an operation writes); `repair.ts` the state hash checked after a merge (`stateDigest`) and the repair from the source of truth (`planRepair`). Their tests share a seeded random edit generator; keep both random tests passing.
  - `storageApi.ts` the Storage API defined with estuary-rpc; `saveApi.ts` saving files out of the app; `importApi.ts` native file and folder picking for import (the app stores picked files itself); `rpc.ts` estuary-rpc over a message channel; `rpcStorage.ts` `Storage` over that API (base64 chunks).
- `client/` (`@nexlibris/client`): React + Vite web app.
  - `backends/` OPFS storage (browser) and the Android, iOS and desktop bridges. `library/LibraryContext.tsx` picks one: the native app's storage when there's a transport (`backends/native.ts`: Android's bridge, iOS's message handler or the desktop app's `window.NexlibrisDesktop`), otherwise OPFS. In the apps `NativeStorage` reads stored files by fetching `/library/files/…`, which the app serves; everything else goes over the transport.
  - `formats/` metadata extraction per format (EPUB, MOBI/AZW3, PDF, TXT/RTF, CBZ/CBR; `opf.ts` an OPF's metadata, an EPUB's or a Calibre `metadata.opf`) and `formats/convert/` in-browser conversion. Plugins add formats and converters (`plugins/formats.ts`, read by `formats.ts`'s `FORMATS` and `converters.ts`'s `CONVERTERS`; `FormatInfo.epub` marks EPUB variants, `isEpub`, `EPUB_FORMATS`; compound extensions like `x4.epub` by `formatFromName`/`stripExtension`). `plugins/crosspoint/xteink/` is the CrossPoint X4/X3 optimizer, a port of the Python in `~/dev/crosspoint/calibre-plugins/crosspoint_reader/` (keep it in step with `optimizer.py`/`textsplit.py`); its options live in `xteink/options.ts`, are part of the converter version, and are asked for when converting (a converter's `options`/`withOptions`, shown by `components/ConvertOptions.tsx` in Convert and Bulk Convert). Connections only send the files a book has, as stored, in their `formats` order; they never convert or rewrite.
  - `isbn/` ISBN checking, Open Library lookup and barcode reading (native `BarcodeDetector`, else zxing-wasm, whose wasm is bundled rather than fetched from its CDN); the "Add by ISBN" UI is `components/IsbnDialog.tsx`, and Open Library's covers for a book (`findCovers`, by ISBN, then title and author), offered in the book editor by the edit button over its cover (`components/CoverPicker.tsx`, a dropdown: choose an image, find on Open Library, or generate one, `library/generateCover.ts`, title and authors on a random muted colour; saved by `library/editCover.ts`, with its colour, the old cover freed).
  - `devices/` the connection model (`types.ts`: a `ConnectionType` reads (`read`: lists a place's books and brings them in), writes (`write`: has a catalog; `single` if it takes books one at a time), or both, and is one of: a `FilesType`, books as files at paths (a reader, a folder; `tools` manage other things on it, each a tab beside its books on the "On it…" screen), an `ExportType`, the static OPDS catalog, an `InstanceType`, another nexlibris, or a `FeedType`, an OPDS server browsed; `formats` it takes, best first, and `preferred` ones it asks to convert to; `SettingField` kinds text, checkbox, `some`). A write connection's **catalog** (`selection.ts`) is `Device.items` (and `Device.files` for books held by particular files) plus what its search matches, added for good when it's opened or synced (`catalogAdditions`); taking a book out (`takeOutOfDevice`) keeps it out of the search too (`excluded`), adding it by hand (`addToDevice`, `addFileToDevice`) lets it back. The sync planner/runner (`plan.ts`, `run.ts`) only adds: books in the catalog not there are sent, files it sent that changed are replaced, nothing else is removed, and a book deleted on the device is taken out of the catalog rather than sent again (`SyncPlan.deleted`); a book whose path changes is moved where the target can, `DeviceTarget.move`, else sent again; files linked by hand, `PlacedFile.linked`, stay put while current; copies of chosen books found on the device, by `devices/match.ts`, are kept or moved into place rather than sent, `PlacedFile.found`; `PlanOptions.only` sends just some books and leaves the rest of the device alone, which `components/SendTo.tsx` ("Send to…" in a book's details and Send in Bulk edit) uses after adding them to its catalog; `components/AddTo.tsx` ("Add to…", on a book or one of its files) only adds them. `send.ts` what to ask before sending (`checkSend`: books without a preferred format a converter can make, files behind their metadata), asked by `components/SendCheck.tsx` in every send and Sync to. `pathTemplate.ts` where books go on a device (`FilesType.folder` and `fileName` are templates: `/library/<author>/[<series>/]`, made safe for FAT), `contents.ts` (what's on a connection against the library, with linking, importing (a type's own `download` first, a folder's manifest) and removing: a book removed from a device is taken out of its catalog, `removeOperations`), and `devices/opds/` the OPDS catalog export (calibre3opds's layout; book files only ever added; `cloudflare/` calibre3opds's Pages files, copied verbatim and written by `cloudflareFiles`, with `search-index.json` for search routing) and its remembered folders. The UI calls them connections (`components/ConnectionsDialog.tsx`: Edit, On it…, Sync from and Sync to by what each can do); the stored model still calls them devices (`library.devices`). A book's details list the catalogs holding it (`components/ItemCatalogs.tsx`). `connections/` the built-in connection types (`index.ts`: `CONNECTION_TYPES`, `connectionType`, `readableConnections`; `active.ts` whether each is active on this device, by its type's `activation`: always (OPDS server and export), by hand (CrossPoint, twins; kept in local state, `active-connections`, so per device), or checked (a folder: chosen here and still there); only active ones are in the Library and can be sent to, and Send to… shows the others as inactive): `opds.ts` the OPDS server and the static export (its formats and Cloudflare settings), `instance.ts`, `folder/` a folder as backup or drive (`FolderTarget` over a `FileSystemDirectoryHandle` remembered per computer, `.nexlibris-library.json` written after each sync by `manifest.ts`, books read back with their details; needs `showDirectoryPicker`). Read connections other than OPDS servers are browsed in the Library too (`['connection', id]` in `browse.ts`, `components/ConnectionBrowser.tsx`). `plugins/` built-in plugins, each adding connection types, formats, converters and/or views (`views/types.ts`: a `LibraryViewType`, a way of showing the books beside grid and list, offered by `views/views.tsx` in the switcher, the View menu and Settings) (`bookshelf/`: the CSS 3D bookshelf view; `graph/`: the force graph view, after `~/Documents/readings`, books joined by their authors, tags and series (`graph.ts`, tags on a quarter of the books left out as hubs) and drawn with 3d-force-graph in the theme's colours (`ForceGraph.tsx`, loaded lazily since three.js is large; the glow only in the dark scheme); `crosspoint/`: the reader type (`crosspoint.reader`, its Model setting X4 or X3 picking the preferred `x4.epub` or `x3.epub`), those formats and their converter (`formats.ts`, `convert.ts`, `xteink/`), the CrossPoint web API client (`client.ts`; `fakeReader.ts` an in-memory reader for tests and stories), its device tools in `tools/` (sleep images, made into screen-sized grayscale BMPs by `sleepImage.ts`; StarDict dictionaries, unpacked and checked by `stardict.ts`; fonts, sorted into families by `fonts.ts`), and `libraryIndex.ts`, the reader's `/.crosspoint/library.idx`, a port of `~/dev/crosspoint/crosspoint-reader/docs/files/library_idx.ksy`: keep it in step with that).
  - `library/libraryFolder.ts` where the library is kept (browser storage, the desktop app's data folder, Android's own storage, or a folder the user picks, laid out by `library/fileLayout.ts` with CrossPoint's path templates; a browser needs `showDirectoryPicker`, so Chrome or Edge), opening it (`LibraryContext` uses it; a browser asks permission for its folder again with a click) and moving it (`relocate` in the browser, copying between folder handles; the apps move it natively behind `libraryFolderApi.ts`: the desktop main process, `desktop/src/libraryFolder.ts`, and Android, `LibraryFolderService.kt`; `LibraryPlace.native` is the app's side). The UI is `components/LibraryFolderDialog.tsx` ("Library folder…"), which says what a folder costs outside the desktop app (slower writes; in a browser, permission asked again after a restart).
  - `library/importFiles.ts` imports: groups files into books (a Calibre book folder with `metadata.opf`, else by name minus the format), takes a Calibre folder's metadata, cover and rating, and matches books already in the library (UUID, ISBN, title and author). Folders come from a folder input, dropped folders (`library/droppedFiles.ts`), or the apps' folder pick (`library/nativeImport.ts`).
  - `library/thumbnails.ts` covers as shown: thumbnails made once and kept in the backend's local files (`readLocalFile`/`writeLocalFile`, under `local/`; not synced or backed up), at `local/thumbs/`, which the apps serve at `/library/local/thumbs/…` as they serve `/library/files/…`. `components/Cover.tsx` shows a thumbnail only while near the viewport; don't display full-size covers in lists.
  - `library/currentlyReading.ts` Currently Reading: books with a reading position that isn't finished or set aside (`ReadingPosition.setAside`, which keeps the place; reading again clears it), shown by `components/CurrentlyReading.tsx` in a notice above the books (`NoticeBox` in `styles/ui.ts`); one click reopens a book at its place. The notice shows each time the app opens while books are being read, until its Hide (not remembered); the Library lists them too, as Currently reading beside All books (`['reading']` in `browse.ts`, last read first unless sorted).
  - `library/bookFields.ts` the fixed fields' labels and kinds as the UI shows and edits them, and the sort keys (title and author sort, falling back to computed ones; first published).
  - `library/coverColor.ts` a cover's most prominent colour (`coverColor`), set at import, on Add by ISBN and by re-reading; `components/Cover.tsx` fills a loading cover with it.
  - `library/dedupe.ts` items with the same title and authors and merging them (as operations); `library/reread.ts` re-reading metadata from the books' own files, filling in only what items lack (never online). `library/fileMetadata.ts` the fingerprint of the metadata written into a file (`FileRef.metadataKey`: set at import when the file says what the item says, by conversion, and by updating files), so a file whose item's metadata changed since is behind it (`isBehind`, shown in `ItemFiles.tsx`). `library/updateFiles.ts` writing the library's metadata into its EPUBs where they say otherwise (`writeEpubMetadata` in `formats/epubMetadata.ts`; DRM-protected files, `epubDrm`, are left alone), each new file checked to read back as the library has it before it replaces the old one, with converted files, reading positions and the text index (`TextIndex.carry`) moved to it. The UI is `components/CleanupDialog.tsx` ("Clean up library…"), a list of cleanups each behind a button, where further cleanups go.
  - Open Library is called only on explicit user action (Add by ISBN, Find on Open Library for a cover); nothing looks things up online on its own.
  - `library/search.ts` the search syntax (Gmail-style `field:value` terms, `or`, `has:`; documented at its top) the one way of choosing books: the search box, connections' catalogs and the books another instance keeps (`components/QueryInput.tsx`, a text box with its match count), categories. There are no separate filters or rules; `library/suggest.ts` completes field names and values in the search dialog (`searchFields`, `fieldSuggestions`).
  - `fulltext/` full-text search: `extract.ts` a file's text in sections (EPUB spine items with chapter names and CFI paths per text node, and TXT, read with `markup.ts`, htmlparser2 rather than the DOM, so they work in a worker; PDF pages and RTF in the page, `extractPage.ts`), `match.ts` queries, word lists and passages (each with its chapter and the locator the reader opens at), `textWork.ts` the heavy work run in a Web Worker (`text.worker.ts`, over `workerRpc.ts`; in the page in tests): extracting, packing (gzipped JSON) and searching, with the word lists it has read cached; `textIndex.ts` the index in the backend's local files (`fulltext/<hash>.json.gz` and `.words.json.gz`, listed in local state's `fulltext`; not synced or backed up), `TextIndexContext.tsx` indexing in the background and `useTextSearch`. The search dialog's "Inside books" mode and `components/TextResults.tsx` show it; bump `EXTRACTOR_VERSION` when extraction changes.
  - `catalogs/` browsing OPDS catalogs on servers: a connection that only reads (`FeedType` in `devices/types.ts`; `opdsServer` in `connections/opds.ts`, beside the OPDS Static Export) that takes no books and has no catalog, only "On it…" (`SourceContents` in `ConnectionsDialog.tsx`) and a place in the Library (`['source', id, ...steps]` in `browse.ts`, a step a page's address or `search:<terms>`, named for the breadcrumbs by `titles.ts`). `opdsFeed.ts` parses OPDS 1 feeds and OpenSearch descriptions (keep it general: calibre3opds's static layout, Gutenberg, calibre's server; editions of one title in a feed, same name, authors and cover, are one book, `mergeEditions`; its one catalog-specific rule, `titleLink`, takes Gutenberg's list entries, links to each book's page, as books whose page is read when opened, `OpdsBook.details`, `withDetails`), `feedCache.ts` keeps pages in local files (`opds/<hash>.json`, parsed: bump `PARSER_VERSION` in `opdsFeed.ts` when parsing changes, and older parses are read again) and checks them with the server after a day (conditional requests where possible), remembers how many pages were loaded (Load more), and searches (the feed's template, else its description's, else the connection's Search address setting; a 404 from a static catalog is no results), `remote.ts` fetches with `fetch` in browsers (CORS permitting; a book that can't be downloaded gets its link instead) and through the desktop main process (`common/src/remoteApi.ts`, `desktop/src/remote.ts`, downloads stored like imports), `credentials.ts` a catalog's sign-in (HTTP Basic), per connection, in local state (`catalog-credentials`; never in the library, so not synced or backed up), sent only to the catalog's own origin; covers that need it are read as blobs (`useCatalogImage.ts`, `fetchSignedInImage`). `addBook.ts` adds a book via `importFiles` and finds the library's copy. A page's places (navigation entries) show as the Library's categories do (`EntryCards` in `components/BrowseEntries.tsx`): a stack under a cover, the place's own thumbnail or the first on its page if cached, else its name drawn as one (`GeneratedCover` in `components/Cover.tsx`), and its count where the feed gives one (`thr:count`) or its page is cached; nothing is fetched for them. `asItem.ts` makes a catalog's books `Item`s (filling `BookMetadata` from what the feed says: series, publisher, language, dates, identifiers, downloads as files), shown only, so `CatalogBrowser.tsx` shows them in the library's own views (grid, list, plugin views), with their covers and an "In library" badge from `components/CollectionDecor.tsx`, which `Cover` and the grid read; a book opens in the right-hand pane as a library book does, `ItemDetail` read-only (its `remote`: no rating, editing, reading or sending; Add to library and its downloads instead), as do the books of readers, folders and twins in `ConnectionBrowser.tsx`; each browser tells `App` (`onDetail`) so the books make room, and in a modal (`embedded`, a connection's "On it…") it opens in another. The UI is `components/CatalogBrowser.tsx`; a catalog that offers search is a mode of the search dialog. Catalogs are read only when the user opens a page, adds the connection or asks for more.
  - `library/browse.ts` where the view is: a path from the Library (calibre3opds's navigation: All books, Currently reading, Authors, Series, the user's `library.categories`, Tags) to books, with the breadcrumbs (`components/Breadcrumbs.tsx`) and the level's entries (`components/BrowseEntries.tsx`); categories are edited in `components/CategoriesDialog.tsx` and written into OPDS catalogs as custom feeds.
  - `sync/` M6 sync in the page: `connect.ts` reaching a pairing's hub by its transport (address prefix `bluetooth:`, `folder:`, else the network), `hub.ts` over the network (Android's relay or `fetch`), `bluetooth.ts` over Web Bluetooth, `bluetoothHost.ts` the Android app hosting over Bluetooth, `folder.ts` through a folder, `files.ts` a hub's files, `instances.ts` other instances as connections (their Sync from, Sync to and single books in `components/InstanceSync.tsx`'s `SyncInstance`; what one shows this one, or offered it, in `components/InstanceContents.tsx`), `hosting.ts` answering paired devices in the desktop app (the hosting screens choose which books' files a device keeps before it pairs: the code carries the choice, `PairResult.keepFiles`, which becomes the rules of that device's own connection, `pairedConnections`; and afterwards, `components/KeptBooks.tsx`), `describe.ts` conflicts in words. Another instance is a connection like a reader: a `Device` of type `nexlibris.instance` whose id is that instance's origin, kept in the library and synced, whose books are the ones that instance gets (it sees only those; sync sends the hub its books' files and fetches this instance's). How this instance reaches it (the `Pairing`: address, key, source of truth, sync base) stays in local state. The UI is `components/ConnectionsDialog.tsx`, with pairing, the sync preview and hosting in `components/InstanceSync.tsx`; there's no separate Sync command. `library/savedFolders.ts` remembers picked folders (catalogs, sync folders) in IndexedDB.
  - `stories/` Storybook's sample library (`sampleLibrary.ts`, a fresh in-memory copy per story, with generated covers) and helpers; stories sit next to their components as `*.stories.tsx`. Config in `client/.storybook/`: every story gets `GlobalStyle` and a `LibraryProvider` over the sample library, and the toolbar's Theme picks light or dark.
  - `reader/` in-app viewers (`Reader` over the library; `BookReader`, the viewer needing only the book). In browsers and the desktop app, Read opens the book in a window of its own (`library/readerWindow.ts`): the app's page at `?read=<item>&file=<hash>`, which `main.tsx` renders as `components/ReaderWindow.tsx` alone, without a library; it asks the library's window for the book over a BroadcastChannel (`serveReaderWindows`, run by `App`) and sends it reading positions to save. Android reads over the library. `components/` UI; `styles/` theme and shared styled components.
  - The top bar and the breadcrumbs stay at the top (`Header` in `App.tsx`, sticky; its height is `--header-height`, which the list's column headers stick below); `Main` isolates its stacking so nothing in the books paints over them. The breadcrumbs' far right holds the view switcher (`components/ViewSwitcher.tsx`).
  - The top bar holds only the name and `components/SearchBox.tsx`, which shows the search (with a clear button) and opens `components/SearchDialog.tsx`, a Spotlight-like search with completions from `library/suggest.ts`, the place searched within, recent searches and the first books found; Enter puts the search back in the bar. Commands are defined once in `App.tsx` and shown as `components/AppMenu.tsx`, a left drawer, in browsers and on Android, or as the desktop app's menu bar (`library/nativeMenu.ts`, built natively by `desktop/src/menu.ts` from `common/src/nativeMenu.ts`). Grid/list, sort and columns are in `components/SettingsDialog.tsx`. Add a new command to both menus. Selection follows `library/selection.ts` (click, Cmd/Ctrl-click, Shift-click; a long press on touch screens, `library/useLongPress.ts`); several selected show Bulk edit (`BulkEditor.tsx`; tags typed anywhere, and creators added there, are completed from the library's by `components/CompletionInput.tsx`, `library/completion.ts`, and past 15 tags or creators on the selection they're typed to remove rather than shown as chips; its Files section removes a format's files, `removeFormat` in `library/freeFiles.ts`; a book's own files are removed one at a time in `components/ItemFiles.tsx`, `removeFiles`, from each file's "⋯" menu, `components/MenuButton.tsx`, a menu of actions for rows that would otherwise be crowded with buttons) and Bulk convert (`BulkConvertDialog.tsx`) in the top bar.
- `android/`: Kotlin WebView shell. Serves `client/dist` from assets at `https://appassets.androidplatform.net` and implements the Storage, Save and Import APIs natively (`StorageService`, `SaveService`, `ImportService`, `RpcRouter`, plus `PeerService` relaying sync calls to a hub, since the page can't call plain http, and moving files between the hub and storage, `LocalHttpService` relaying a CrossPoint reader's calls the same way, `BluetoothHostService` a BLE GATT server carrying sync messages for the page to answer, `ImportFolder.kt` walking a folder picked for import, `SyncFolderService`/`DocumentTreeStorage` the user-picked USB sync folder through the storage provider, `LibraryFolderService` the library's folder (the app's own storage or one picked with the folder picker, `TreeFolders`, kept with a lasting permission and no storage permission; moved by copying, and the storage, imports, hub files and `/library/` serving follow it, `LibraryTree`), `NativeBridge`, a `WebViewCompat` web message listener limited to the app's origin); the camera, for ISBN scanning, is granted only to the app's own pages. Library logic stays in TypeScript.
- `ios/`: Swift WKWebView shell, the same as Android's (keep the two in step; library logic stays in TypeScript). The page is served at `app://nexlibris/` (a scheme the app serves, which WebKit treats as secure) by `AppSchemeHandler` (the built `client/dist`, copied into the app as `www` by `scripts/copy-web-app.sh`, and `/library/…` as Android serves it). The native side is the Swift package `NexlibrisKit` (Foundation, WebKit and CoreBluetooth only, so it builds and tests on macOS): Swift ports of Android's services, `FileStorage` (one storage for the app's own, the library's folder and the sync folder: folders picked in Files are plain files inside their security scope, kept by `Bookmarks`), `RpcRouter` and its route tables, `SaveService` (the export picker), `ImportService`, `PeerService`, `LocalHttpService`, `LibraryFolderService`, `SyncFolderService`, `BluetoothFraming` and `BluetoothHostService` (a CoreBluetooth peripheral), and `NativeBridge`, a `WKScriptMessageHandlerWithReply` named `nexlibris` answering the app's own main frame only (`client/src/backends/iosBridge.ts`; the page's `postMessage` promise resolves with the reply, so calls carry no ids). Folders in iCloud Drive are read through their placeholders (`.Name.icloud`), downloaded on demand. `App/` is the UIKit shell (`WebViewController`: the web view below the status bar and above the keyboard, the page keeping clear of the notch and home indicator itself, links out to the browser, the camera for the app's own page; `Pickers`: the document pickers, which the bridge's queues wait on). The Xcode project is generated from `project.yml` with XcodeGen (`xcodegen` in `ios/`; commit the regenerated `nexlibris.xcodeproj`). The client treats Android and iOS alike through `client/src/backends/mobileBridge.ts` (`inMobileApp`, `mobileTransport`, `mobileApp`); check `inAndroidApp`/`inIosApp` only where they differ (wording, the sync folder).
- `desktop/`: Electron shell. Serves `client/dist` at `app://nexlibris/` and implements the Storage, Save and Import APIs in the main process over native files (`fileStorage.ts`, `saveService.ts`, `importService.ts`, served with `createMessageHandler`); the preload exposes `window.NexlibrisDesktop.rpc` for those, plus the menu bar (`setMenu`, `onMenuCommand`; `menu.ts` checks what the page sends and adds the app menu, Quit and Window). On macOS the window has no title bar (`titleBarStyle: 'hiddenInset'`): the preload's `titleBarInset` and `onFullScreen` let the page mark `<html data-title-bar="inset">` (`followTitleBar` in `client/src/backends/desktopBridge.ts`), so the top bar leaves room for the window buttons and moves the window (`-webkit-app-region`), and the reader gets a drag strip; anything covering the top bar (a `dialog`, or `[data-covers-window]`) turns the drag region off. Stored files are read from `app://nexlibris/library/files/…`, as on Android. The library's folder is the data folder's `library`, or one chosen in the app (`settings.json` in the data folder; `libraryFolder.ts` moves it, and `main.ts` switches to it without restarting); in a folder of the user's, the books placed in it are served too, and imports and synced files land in its `.nexlibris/`. A book's window (`isReaderUrl`) is allowed to open as another app window; menu commands and sync calls go to the library's window (`libraryWindow`). As a sync hub, `syncHost.ts` serves the sync API on the LAN and relays calls to the page (the preload's `servePeers`), serving and storing files itself; pairings live in `<library>/local/sync-host.json`. Bundled with rolldown (`dist/main.js`, `dist/preload.cjs`). `npm start -w desktop` runs `scripts/start.js`, which on macOS launches a renamed copy of Electron (`desktop/.app/nexlibris.app`, ignored by git) so the app shows as nexlibris; `productName` in `desktop/package.json` sets the app name and so its data folder.
- `server/`: M4's Node server (`npm run server`; options in `src/config.ts`, `help` lists them). `src/app.ts` wires the server: the server API (`common/src/serverApi.ts`) and the sync API per account, estuary-rpc APIs served by estuary-rpc-server's `createApiServer`, and the web app as its `staticFiles`. `src/api/` holds the rest: `context.ts` what endpoints are given (`Services`, the `Caller` context with its account or pairing), `request.ts` what a request says (cookie, bearer token, same-site checks), `middleware.ts` estuary's options (`authenticate` checks the session cookie, an app's session token (bearer; `Credentials.token` signs in for one, and `apiHeaders` sends CORS headers), or a sync key and puts the account or pairing on the context; middlewares add an optional session and refuse cross-site changes; `mapError` gives library errors their statuses, as endpoints throw estuary-rpc's `ApiError`), and the endpoints by group (`auth.ts`, `library.ts`, `sync.ts`, sharing `files.ts`); books' files streamed through raw endpoints (estuary-rpc's `RAW` transport, path parameters) at `api/library/files/<hash>` and `api/sync/files/<hash>` (`syncFilesMeta`). `src/accounts.ts` accounts and sessions (scrypt, hashed session tokens in an HttpOnly SameSite=Strict cookie, sign-in rate limits), `src/libraries.ts` a `StoredLibraryBackend` per account, its JSON in the data folder and its files in an `ObjectStore` (`src/objectStore.ts` a folder, `src/s3.ts` an S3-style bucket signed with SigV4 over `fetch`: AWS, GCS, B2, custom endpoints), `src/pairings.ts` the sync keys of devices paired with an account (hashed). Calls that change anything with the cookie must be same-origin JSON. The client side: `common/src/serverBackend.ts` (`ServerLibraryBackend`, the library in the account; `serverClient`; `isSignedOut` is a 401), `client/src/library/account.ts` (the server and session: a browser's page uses the server it came from, none from a static host; the apps choose one by address, `chooseServer`, kept with its token in local storage, and call it via `serverConnection`: the desktop app through its main process, `common/src/appServer.ts` and `desktop/src/serverProxy.ts`, Android through `localFetch` on the local network, else directly over https), `components/AccountDialog.tsx` (Account… / Sign in…, in both menus on a page from a server and always in the apps, which choose the server there, `ServerChoice`), the `cloud` place in `library/libraryFolder.ts` (`moveToCloud`/`moveFromCloud`, over `copyToCloud`/`copyFromCloud`; the apps copy rather than move, `copyAppLibraryToCloud`, and `openDeviceLibrary` opens the device's again; `LibraryContext` asks to sign in, `SignInScreen`, when the account's library needs it), and `PairServer` in `components/InstanceSync.tsx` (keeping a copy in the account, synced as with another instance). `NEXLIBRIS_SERVER=<url> npm run dev` proxies `/api` to a server.
- `icon.png` is the source of every app icon. After changing it, run `python3 scripts/make-icons.py` (needs Pillow): it writes the squircle favicons (`client/public/`), the desktop icon (`desktop/assets/icon.png`) and the Android launcher icons (`android/.../res/mipmap-*`).

## Commands

Run from the repo root (Node 24 via nvm; in a non-login shell, put `~/.nvm/versions/node/v24*/bin` on PATH).

- `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`, `npm run dev`.
- Storybook: `npm run storybook -w client` (http://localhost:6006), `npm run build-storybook -w client` (to `client/storybook-static/`, ignored by git). Add a story when adding or changing a component; one that needs the library can read it from context, which holds the sample library. Run test, typecheck, lint and build before calling work done.
- Lint is oxlint (`.oxlintrc.json`), not ESLint: typescript-eslint doesn't support TypeScript 7. Rules that only flag idioms used on purpose here are off in the config, with the reason; a one-off exception gets `// oxlint-disable-next-line <rule> -- why`.
- Single workspace: `npm test -w client`, or `npx vitest run src/path` inside a workspace.
- Desktop: `npm run desktop` (builds, then runs Electron). `NEXLIBRIS_LIBRARY_DIR` picks the library folder. npm may skip Electron's install script; then run `node node_modules/electron/install.js`.
- iOS: `npm run ios` (needs Xcode; builds for the simulator), or open `ios/nexlibris.xcodeproj`. Native tests `cd ios/NexlibrisKit && swift test` (with only the Command Line Tools, add the Swift Testing paths given in the README).
- Android: `npm run android`; native tests `cd android && ./gradlew testDebugUnitTest lintDebug`. Needs `JAVA_HOME` set to Android Studio's JBR (the system Java is 8) and `android/local.properties` with `sdk.dir`. Builds use compileSdk 36 and build-tools 36.1.0; newer AndroidX releases need AGP 9 / API 37.

## Conventions

- Mutate libraries only through operations; never edit `Library` objects directly in the UI.
- Changing the stored shape of a library (types in `common/src/types.ts`, or an operation's shape) means bumping `SCHEMA_VERSION` and adding a step to `MIGRATIONS` in `common/src/migrate.ts`, with a test.
- Prefer TypeScript implementations of format parsing and conversion that run in the browser.
- Styling uses styled-components with transient `$props`; theme values are CSS variables in `styles/GlobalStyle.ts`, dark when the system is unless Light or Dark is picked in Settings (`styles/appearance.ts`, `<html data-theme>`); code that needs to know reads `isDark`/`onAppearanceChange` there rather than `prefers-color-scheme`. Reuse `styles/ui.ts` before adding new primitives. No CSS files.
- Book HTML (descriptions, EPUB content) is untrusted: render it with `RichText`, which rebuilds allowlisted tags as React elements. Never use `dangerouslySetInnerHTML`.
- Tests run in happy-dom with resource loading disabled (`client/vite.config.ts`); keep it that way so tests never hit the network. Sample books live in `client/src/formats/fixtures/`. happy-dom differs from browsers: parse XML with `formats/xml.ts` (happy-dom rejects some valid XML declarations), and mock the Kindle parser in import tests (under Node it fetches resources and writes to disk).
- Code style: single quotes, lines around 120 columns (some run longer). There's no formatter config, so don't run Prettier over whole files: it rewraps untouched code. Format only what you write, by hand or on a scratch copy.
- Any change to the Storage, Save or Import API must be made in `common/src/storageApi.ts`/`saveApi.ts`/`importApi.ts`, `android/.../RpcRouter.kt` plus `StorageService.kt`/`SaveService.kt`/`ImportService.kt`, `ios/NexlibrisKit/.../RpcRouter.swift` plus `FileStorage.swift`/`SaveService.swift`/`ImportService.swift`, and `desktop/src/fileStorage.ts`/`saveService.ts`/`importService.ts`, with tests on every side. The SyncHost API is desktop-only; the Peer, localHttp, bluetoothHost, usbFolder and window APIs are Android's and iOS's (change both).
- Save files out of the app with `client/src/library/saveFile.ts`, not `<a download>` alone: downloads do nothing in the Android WebView. For big files use `saveParts` (the backup does, with `library/zip.ts`), and call it before awaiting anything so Chrome's save picker still has the click's user activation.

## Dependencies to know about

- `epubier` is linked from `../epubierjs` (`file:` dependency), which must be checked out next to this repo. nexlibris uses its built `dist/`, so run `npm run build` there after changing it. Its `position` and `onLocationChange` options exist for nexlibris's reading positions, `onThemeChange` for colouring the title bar strip and Android's system bars like the reader, and `replacements: 'base64'` for opening image-heavy books quickly in the Android WebView; `src/patches.js` there fixes epub.js's base64 mode.
- `estuary-rpc`, `estuary-rpc-client` and `estuary-rpc-server` are linked from `../estuary-rpc` (`file:` dependencies; that repo must be checked out next to this one, and built: `npx tsc` in each package), for changes made there and not yet published. Vite pre-bundles them (`optimizeDeps`), as their `dist/` is CommonJS. `rpc.ts` keeps its own client types (`MessageClient`), which estuary's clients are cast to (`httpClient` in `common/src/rest.ts`).
- Over HTTP, APIs follow estuary-rpc's REST conventions (200 JSON, 204 for none, errors `{ status: 'error', message }` with a status, thrown on the client as `ApiError`): the server with estuary-rpc-server, clients with estuary-rpc-client over `fetch` (`httpClient`, `reaching`), and hubs that relay calls to the page (desktop, Bluetooth) answering with `restReply`. No envelopes of our own on the wire.
